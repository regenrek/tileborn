# ADR-0017: Petwars feature parity roadmap

- Status: Proposed
- Date: 2026-05-24
- Revised: 2026-06-01 (Round 2: strategic intent, three-lane ownership classification, follow-up ADR renumber reconciliation)
- Deciders: Tileborne core team
- Tags: roadmap, parity, simulation, editor-ui, runtime, ipc, plugin-boundary, assets, netcode, audio, research

## Context

Tileborne now has ADRs for the v0.1 rendering and terrain blockers:

- ADR-0014 owns plugin projector rendering, snapshot store/interpolation, multiplayer protocol cleanup, follow camera, projectiles, HUD insets, and the battle-royale renderable contract.
- ADR-0015 owns bundled asset registration, plugin-owned bundled assets, F1/F2/F3/F4 live fixes, and worker-safe runtime entry cleanup.
- ADR-0016 owns ERW Ancient Tiled rule integration, rule-pack data ownership, authoring UI for wangsets/terrain, and runtime application of those rules.

This ADR records what remains after those exclusions. Petwars is used as a private product reference, not as an architecture template. The target is plugin-neutral Tileborne functionality that lets a Petwars-like product rebuild its gameplay/editor loop on top of public packages without leaking private names, `.pwmap` formats, ERW private content, or battle-royale-specific shortcuts into the engine.

The v0.1 synthesis already identified Cloudflare room lifecycle, Pixi/ECS, plugin contribution points, battle-royale loop, local multiplayer, and shadcn editor polish as v0.1 workstreams. This ADR starts the next roadmap: playable parity beyond rendering and ERW terrain.

## Strategic intent

This roadmap pursues two outcomes at once, and the second must not compromise the first:

1. **Finalize a first-class OSS game maker.** Tileborne (the OSS monorepo) is the product: a neutral 2D game editor, runtime SDK, plugin API, and game-host template that any game can build on. Every parity capability below is first designed as a reusable, brand-neutral engine or plugin contract.
2. **Build the Petwars Battle-Royale game ("petwars") on top of it, by reuse only.** Petwars is delivered as the composition of (a) the OSS engine packages, (b) the `@tileborne/plugin-battle-royale` plugin, and (c) the private `petwars-product` repo. Petwars proves the maker is real, but contributes no engine logic back into it.

This produces a strict three-lane ownership model, anchored by [ADR-0009](./0009-three-repo-split-private-petwars-boundary.md) and the `docs/adrs/README.md` boundary note:

| Lane                                | Repo / package                                                                                                                                                                                                                                                                                 | Owns                                                                                                                                                                                                                 | Must never own                                                                                                                                |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **Shared OSS engine**               | `tileborne` monorepo: `packages/core`, `packages/runtime`, `packages/ipc-contracts`, `packages/plugin-api`, `packages/asset-pipeline`, `packages/sdk-tileset`, `packages/ui`, a future `packages/simulation`, `apps/desktop` (editor), `apps/game-host` (template), `apps/game-client` (shell) | Neutral schemas, deterministic systems, plugin contribution slots, editor UX, IPC contracts, runtime/host orchestration                                                                                              | Plugin names, `petwars`/`grassland`/`erw:`/`.pwmap` literals, game-specific balance/content                                                   |
| **BR / game-mode plugin**           | `packages/plugin-battle-royale` (and future `tileborne-plugins`)                                                                                                                                                                                                                               | Game-mode gameplay logic, balance data, content packs, mode menu surfaces, BR-specific authoring contributions, registered through public plugin APIs                                                                | Engine-internal ownership; private product brand literals; deploy config                                                                      |
| **petwars-product** (thin consumer) | `/Users/kregenrek/projects/games/petwars-product`                                                                                                                                                                                                                                              | Branding (`branding/tokens.json`, logo, copy, fonts), private assets (`assets/`), authored maps (`maps/`), BR plugin selection (`plugins/`), Cloudflare/Alchemy deploy (`deploy/`), build orchestration (`scripts/`) | **Any engine or gameplay logic.** Consumes `@tileborne/core` + the `tileborne` CLI + the BR plugin; supplies content/config/brand/deploy only |

Evidence that `petwars-product` is already a thin consumer (this is the target state, not aspirational): its only runtime dependency is `@tileborne/core` for content hashing (`petwars-product/package.json:23-25`); it consumes `@tileborne/cli` / `@tileborne/game-host` / the BR plugin externally (`petwars-product/README.md:9-11`, `petwars-product/AGENTS.md:13-14`); its build is pure composition — install BR plugin stub, `tileborne asset import`, `tileborne game build --target cloudflare` + brand overlay, Alchemy deploy (`petwars-product/README.md:43-52`); its plugin folder ships only a compiled stub (`plugins/battle-royale/dist/runtime.js`), not source. A separate architecture-ownership analysis this session confirmed these boundaries are clean.

**Roadmap consequence:** for every feature below, the design question is "which engine package or plugin owns this?", never "what does petwars need?" If a capability would require petwars-product to hold engine logic, the design is wrong and the logic belongs in the shared engine or a plugin. `petwars-product` only ever appears as a consumer that supplies content, config, brand, or deploy.

## Decision

Adopt a phased parity roadmap for the residual Petwars feature surface:

1. Phase A, v0.2 playable parity: enough neutral simulation, catalog, map package, IPC, editor object placement, HUD, and non-BR mode plumbing to run a basic multiplayer combat/loot loop without relying on private Petwars code.
2. Phase B, v0.5 authoring depth: full object/loot/skin/weapon authoring, matchmaking, telemetry, asset importers, and richer editor diagnostics.
3. Phase C, v1.0 polish: audio, durable replay, spectator/pause/results polish, accessibility, and gameplay UI polish.

This ADR does not implement code. It creates owning research workstreams and follow-up ADR slots so each major feature can get a narrower design, task graph, and tests before implementation.

Hard exclusions:

- Do not re-file ADR-0014 runtime rendering, snapshot interpolation, projectiles, follow camera, HUD insets, or BR projector contract.
- Do not re-file ADR-0015 bundled-asset registration, plugin-owned bundled assets, F1/F2/F3/F4 live fixes, or worker-safe runtime entry fixes.
- Do not re-file ADR-0016 ERW rule engine, rule-pack ownership, wangset/terrain authoring UI, or runtime rule application.
- Do not reopen cancelled orphans `t-v8y1`, `t-c857`, `t-13dq`, or `t-ne6z`.

## Plugin-neutral architecture

PNNM means "plugin-neutral neutral model": engine packages own reusable engine contracts; plugins own game-specific content and policy. Nothing engine-side may reference plugin names.

| Workstream                         | Runtime owner                                 | First-fix owner                                              | Canonical long-term owner                                                                                  | Competing owners that are wrong                                                    | Cleanup direction                                                                                       |
| ---------------------------------- | --------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Simulation and combat math         | Worker/runtime tick paths                     | `packages/plugin-battle-royale` only for current BR behavior | `packages/core` or new `packages/simulation`, worker-safe                                                  | Renderer, Electron main, game-host, plugin-specific packages as the only owner     | Extract pure schemas and deterministic systems; leave plugin-specific balance data in plugins.          |
| Game-object catalog and validation | Runtime map loading and editor validation     | Current plugin object placement/export paths                 | `packages/core` or `packages/simulation` for schema/validation; plugins for content packs                  | `apps/desktop/src/renderer`, `apps/game-host`, `packages/runtime` as policy owners | Move families, roles, item/loot schema, collision footprints, and validation into neutral packages.     |

Forbidden edges and boundary tests required per workstream:

- `packages/core`, `packages/runtime`, `packages/ipc-contracts`, and any future `packages/simulation` must not import from `packages/plugin-battle-royale`, `apps/desktop`, `apps/game-host`, private Petwars paths, `.pwmap`, `petwars`, `grassland`, or `erw:` literals.
- `apps/desktop/src/renderer/**` must not import simulation internals, Cloudflare/game-host internals, Node, Electron, plugin executable code, or plugin deep paths. It may consume IPC clients and declarative/projection view models.
- `apps/game-host` remains the only Cloudflare Durable Object/WebSocket lifecycle owner. Runtime packages must not know about Cloudflare bindings.
- Plugin-shipped catalogs, weapon packs, pet packs, map packs, loot tables, and audio buses must register through public plugin contribution or bundled data APIs. Engine-side registries must use plugin-neutral IDs.
- New public contracts in `packages/core`, `packages/runtime`, and `packages/ipc-contracts` use Effect v4 patterns: `Schema.Class`, branded IDs, `Schema.TaggedClass` variants, and `Schema.TaggedErrorClass` for typed failures.
- Boundary tests should forbid private-product tokens, plugin-name imports in engine packages, renderer imports of simulation internals, Node/Electron imports in worker-safe entries, and `AssetPackManifestAsset`/`AssetId` reuse for plugin-bundled runtime data unless explicitly allowed by ADR-0015.

## Ownership classification: shared engine vs BR plugin vs petwars-product

This is the keystone classification this roadmap exists to lock. Each parity capability is assigned to exactly one **canonical owner lane**. The `petwars-product` column is intentionally almost empty: it is always a consumer that supplies content, config, brand, or deploy — never logic. "(consumes)" means petwars-product gets the capability for free by composing the engine + BR plugin.

Cross-cutting rule restated: **no row assigns engine or gameplay logic to petwars-product.** Where a row lists a `petwars-product` artifact, it is always content (`assets/`, `maps/`), brand (`branding/`), plugin selection (`plugins/`), or deploy (`deploy/`). The "first-class OSS game maker" is satisfied when a _different_ product could swap in its own thin consumer repo and ship a different game from the same engine + a different mode plugin.

## Risks and mitigations

1. Private Petwars leakage. Mitigation: boundary tests block `petwars`, `.pwmap`, `grassland`, private paths, and plugin names in engine packages.
2. Over-generalized engine. Mitigation: P0 extracts only primitives needed by at least two game modes or by editor/runtime boundaries; plugin-specific balance remains plugin data.
3. Duplicate catalog owners. Mitigation: one catalog schema owner in `packages/core` or `packages/simulation`; plugin packages own content entries only.
4. Renderer shortcuts. Mitigation: renderer consumes IPC/projected DTOs and declarative contribution data, never simulation internals or game-host bindings.
